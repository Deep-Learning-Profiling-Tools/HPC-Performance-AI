# Frozen golden references (`tools/golden`)

Correctness of a benchmark run is judged by comparing its outputs with a **frozen golden
reference**: the outputs of the original, unmodified build on the reference GPU (NVIDIA B200,
dgx003), captured once per registered input and never regenerated by a normal run. The CPU
reference implementations that many benchmarks carry (a serial host re-implementation, a
`verify.py`, a Sequential/OpenMP execution path) run **only once, offline**, to validate that
capture -- never on a default path (a plain run, ctest, `tools/inputs` measure/check,
`tools/timing`, the optimization loop), and never as an automatic fallback.

The same frozen B200 reference is the oracle on every other platform (H200, MI355X, ...); the
tolerances are the benchmarks' own upstream tolerances for their GPU-vs-CPU checks, so a
legitimate implementation on another architecture (another FMA contraction, libm, summation
order) passes exactly when it would have passed the original CPU comparison (see "Tolerance
budget").

| file | what |
|---|---|
| `hpcperf_golden.h` | header-only C/C++: `hpcperf_cpu_reference_enabled()` (the gate, **off by default**), `hpcperf_golden_output()` / `_begin` / `_append` / `_end` (output capture) |
| `hpcperf_golden_capture.py` | the Python twin of the capture (for `verify.py` CPU arrays) |
| `hpcperf_golden.py` | `make` (one-time, CPU-validated freeze), `check` (compare a capture), `run` (ctest entry), `status`, `validate` |
| `tests/run_all.sh` | CPU-only tests (fake repository and benchmarks; no GPU) |

## Switches

| variable | effect | who sets it |
|---|---|---|
| `HPCPERF_CPU_REFERENCE=1` | the benchmark runs its own CPU reference and prints its pass line; also enables the offline CPU cross-check scripts of Level 2 (`check_sequential.sh`, `check_reference.sh`, `validate.sh` offline mode) | **only** `hpcperf_golden.py make` (or a person, explicitly). `tools/inputs` measure/check and `tools/timing` drop it from the environment; `tools/timing` cases cannot set it |
| `HPCPERF_GOLDEN_DUMP=<dir>` | the program writes each declared output to `<dir>/<name>.bin` plus one line in `<dir>/manifest.jsonl` (name, dtype, count, bytes, sha256) | the `check:` block (`run_env`), `make`, `run` |
| `HPCPERF_GOLDEN_MODE=hash` | record the sha256 only (huge outputs compared exactly, e.g. channel_shuffle's 23-30 GB) | the benchmark's `golden.mode` |
| `HPCPERF_SKIP_VERIFY=1` | unchanged meaning for the remaining property checks (lud, graph_coloring); for every converted benchmark it is implied | `tools/timing` |
| `HPCPERF_RANDOM_SEED=time\|<n>` | fir / color_histogram only: a non-registered random input (the registered inputs use seed 1); such a run FAILs the golden check, and tools/inputs, tools/golden run and tools/timing never pass it on | a person, explicitly |
| `HPCPERF_GOLDEN_STORE=<dir>` | where the raw bytes of tolerance-compared outputs live (default `<repo>/.golden-store`) | the environment |

Call sites capture **after** the timed region (ROI) and after the final device-to-host copy;
with no `HPCPERF_GOLDEN_DUMP` the capture is a no-op, so timing is unaffected.

## The registry (`inputs.yaml`)

```yaml
golden:
  mode: data                      # data | hash
  binary: build/level2/<app>/...  # run.sh entries only: the executable run.sh launches (provenance, staleness)
  cpu_check:                      # how `make` validates the capture ONCE
    pass_regex: '^PASS$'          #   the CPU reference's own pass / fail lines
    fail_regex: '^FAIL$'
    command: [python3, '{bench_dir}/verify.py', '{exe}', '{args}']   # optional: an external checker that runs the binary
    after_run: true               # optional: run the plain GPU command first, then `command` validates THAT run ({log})
    env: {KRIPKE_SEQ_LOG: '{run_dir}/sequential.log'}                # optional, templated
  outputs:
  - name: p                       # or match: <regex> + count: N (many captures with one rule)
    dtype: f32                    # f32 f64 i8 u8 i16 u16 i32 u32 i64 u64
    rule: {metric: max_abs, tol: 1.0e-3}
    cpu: p.cpu                    # the CPU-reference capture (d0); or {log: {file: <template>, regex: ...}}; or null
    basis: <the upstream check this reproduces, file:line>
  # Level 2: an output printed in the log instead of captured
  - name: particle_count
    dtype: f64
    log: {regex: '^\s*iter \d+: particle count=(?P<value>[0-9.eE+-]+),'}
    ...
check:                            # the registry's correctness check (tools/inputs/README.md)
  kind: post_run
  run_env: {HPCPERF_GOLDEN_DUMP: '{run_dir}/golden-capture'}
  command: [python3, '{repo}/tools/golden/hpcperf_golden.py', check, '{bench_dir}', '{input_id}', --dump, '{run_dir}/golden-capture']
  pass_regex: '^PASS: golden check'
  fail_regex: '^FAIL: golden check'
  covers: all
```

Rules (each reproduces the benchmark's existing check, metric and tolerance, cited in `basis`):

| metric | value | used for |
|---|---|---|
| `exact` | sha256 equality | integers, permutations, bitwise-checked outputs (memcmp / ==) |
| `max_abs` | max \|a - g\| | e.g. adam, bilateral_filter, black_scholes, burgers_equation |
| `max_rel1p` | max \|a - g\| / (1 + \|g\|) | RAJAPerf `compareArrays`, spadd, spgemm, backprop, hotspot, nearest_neighbor |
| `max_rel` | max \|a - g\| / \|g\| | pagerank, Kripke |
| `max_relabs` | max \|a - g\| / (rtol \|g\| + atol), tol 1 | ExaCMech |
| `l1_rel` | Σ\|a - g\| / Σ\|g\| | bezier_surface |
| `l2_rel_sq` | Σ(a - g)² / Σg² | spmv |
| `rmse` | sqrt(mean (a - g)²) | hotspot_3d |
| `trunc_int` | max \|trunc a - trunc g\| and the share of pixels that differ by >= 1 | srad_v1 (an (int)-written image) |

A non-finite value where the golden is finite always fails; an output of another shape fails; a
capture whose bytes do not match its recorded sha256 fails; a missing golden blob fails.

## Tolerance budget

`make` also captures the CPU reference's own array (`cpu:`) and records
`d0 = metric(B200 golden, CPU reference)`. The check allows `tol_effective`, chosen so that by the
triangle inequality a candidate within `tol_effective` of the golden is **strictly** within the
upstream tolerance of the CPU reference -- replacing the CPU reference by the golden does not loosen
the original criterion:

| metric | tol_effective |
|---|---|
| `max_abs`, `rmse` | `tol - d0` |
| `max_rel1p`, `max_rel`, `l1_rel` | `(tol - d0) / (1 + d0)` (the golden's magnitude in the denominator is at most `1 + d0` times the CPU reference's) |
| `max_relabs` (tol 1) | `(1 - d0) / (1 + rtol d0)` |
| `l2_rel_sq` | `((sqrt tol - sqrt d0) / (1 + sqrt d0))^2` |
| `trunc_int` | `tol - d0` levels and `frac_tol - share0` (share of pixels >= 1 level apart: conservative) |

Outputs compared exactly need no budget: the original check already proved golden == CPU
reference bit for bit. When the CPU reference keeps no comparable array, d0 is not measured,
`tol_effective = tol`, and the reference says so (`d0_source`).

## `make`: the one-time, CPU-validated freeze

```bash
python3 tools/golden/hpcperf_golden.py make level1/adam n10000-t200     # or --all
```

It refuses (exit 2) when: the benchmark directory, `tools/golden` or `tools/timing/roi` have
uncommitted changes (a golden comes only from committed, unmodified sources -- never from an
optimization candidate or an agent workspace); the binary is older than its sources; a reference
already exists (replacing one needs `--replace --reason "..."`, and the new file records what it
replaced). It runs the build once with `HPCPERF_CPU_REFERENCE=1` and `HPCPERF_GOLDEN_DUMP`
(or, `after_run`, the plain GPU run and then the CPU cross-check of that run), requires the CPU
reference's pass line, exit 0 and no fail line, measures d0 per output and writes:

* `<bench_dir>/reference/<input_id>.json` (schema `hpcperf-golden-1`, **committed**): the workload
  identity of the input, the frozen spec, per output dtype / count / sha256 / statistics / rule with
  `d0_vs_cpu_reference` and `tol_effective`, and the provenance (host, GPU name + UUID + driver,
  CUDA Toolkit, git HEAD, binary + sha256, command, the CPU validation's pass line and log sha256,
  the tool's own sha256);
* for tolerance-compared outputs, the raw bytes in the content-addressed store
  `$HPCPERF_GOLDEN_STORE/sha256/<aa>/<sha256>.bin` (**never in git**; large).

## The correctness gate (optimization candidates)

`check` and `run` read the registry and the frozen reference only from the canonical benchmark directory
(`<repo>/level<N>/<name>`); a copy -- an optimization candidate's workspace -- is refused, so a candidate can
never supply its own reference or rules, and `make` refuses a copy as well. `run --exe <candidate binary>`
runs that binary on the registered input (no CPU reference, capture into a private directory) and compares;
`--json <file>` writes the machine-readable verdict (`hpcperf-golden-verdict-1`: verdict, reason, every
output's metric value and limit, the reference file and its sha256, the binary and its sha256, the command,
exit code). An optimization harness accepts a candidate's timing only with a PASS verdict whose
`binary_sha256` is the sha256 of the binary it timed. Exit 0 only for PASS; a missing reference, a missing or
corrupted blob, a changed spec, another workload, a missing or partial capture, a non-zero exit are all FAIL.

`store-put <file>` / `store-get <sha256>`: content-addressed storage of a frozen reference that is a file
rather than captured arrays (e.g. a plotfile archive); `store-get` verifies the sha256 and fails when the
blob is missing or corrupted.

## Cost

The capture computes SHA-256 with the system's libcrypto when it can be dlopen'ed at run time (CPU SHA
instructions: ~2 GB/s on the Xeon 8570; `HPCPERF_GOLDEN_PORTABLE_SHA=1` forces the portable code, ~0.2 GB/s);
the digest is the same. Measured on a B200 (capture overhead on top of the plain run / Python comparison):
channel_shuffle g2-w224-h224 (23 GB, hash) +24 s / 0.3 s (was +125 s); bezier_surface n8192 (0.8 GB)
+1.3 s / 3.2 s (was +5.0 s / 8.2 s); burgers x8200 (1 GB) +1.6 s / 2.6 s; spgemm m100000 +3.1 s / 2.5 s.

## `check` / `run`

`check` reads the frozen reference and the run's capture (or, for log outputs, the run's log),
verifies the workload identity and that the registry's spec still equals the frozen one (a rule
changed after freezing is a FAIL until an explicit `make --replace`), compares every output and
prints `PASS: golden check <bench>/<input> ...` or `FAIL: golden check ...` (exit 0 / 1). It never
runs a CPU reference and never writes a reference. `run` (the ctest entry) runs the binary once
without the CPU reference, capturing, then checks.

## What is not (or not yet) a golden comparison

* NPB `cg ep ft is mg`: official class reference values (unchanged).
* `lud` (L*U residual), `gaussian_elimination` (residual of the printed solution), `graph_coloring`
  (validity; its valid colorings are not unique and differ run to run): property checks, unchanged.
* `ao_bench`: already a frozen B200 image hash (`reference/iter100.sha256`), unchanged.
* `binary_search`: has no check in the default build (`verify()` only under `-DDEBUG`) -- pending.
