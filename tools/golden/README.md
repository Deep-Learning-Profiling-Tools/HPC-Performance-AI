# Frozen golden references (`tools/golden`)

Correctness of a benchmark run is judged by comparing its outputs with a **frozen golden
reference**: the outputs of the original, unmodified build on the reference GPU (NVIDIA B200,
dgx003), captured once per registered input and never regenerated by a normal run. The CPU
reference implementations that many benchmarks carry (a serial host re-implementation, a
`verify.py`, a Sequential/OpenMP execution path) run **only once, offline**, to validate that
capture -- never on a default path (a plain run, ctest, `tools/inputs` measure/check,
`tools/timing`, the optimization loop), and never as an automatic fallback.

The same frozen B200 reference is meant to be the oracle on every other platform (H200, MI355X,
...; none of them tested yet). The tolerances are the benchmarks' own tolerances for their GPU-vs-CPU
checks -- upstream's where upstream defines one; where upstream's check was missing, too loose to
see a wrong result, or did not observe the output, a project criterion fixed from measured
legitimate vs wrong implementations and documented in the benchmark's README and `basis` (nbody
positions / velocities and kinetic energy, pagerank, hotspot_3d's max_abs gate, the correctness
probes, e.g. spmv's probe-real and srad_v1's probe-edges-n20). A legitimate implementation on another
architecture (another FMA contraction, libm, summation order) therefore passes exactly when it
would have passed the CPU comparison at that tolerance (see "Tolerance budget").

| file | what |
|---|---|
| `hpcperf_golden.h` | header-only C/C++: `hpcperf_cpu_reference_enabled()` (the gate, **off by default**), `hpcperf_golden_output()` / `_begin` / `_append` / `_end` (output capture) |
| `hpcperf_golden_capture.py` | the Python twin of the capture (for `verify.py` CPU arrays) |
| `hpcperf_golden.py` | `make` (one-time, CPU-validated freeze), `check` (compare a capture), `run` (ctest entry), `status`, `validate` |
| `golden_artifacts.py` | distribution of the store: `pack` (deterministic bundles of the blobs the committed references name), `fetch` (verified install into the store), `verify`, `lock-check`, `plan` -- see [DISTRIBUTION.md](DISTRIBUTION.md) |
| `scrub_provenance.py` | `plan` / `apply` / `verify --against REV`: removes machine identity (host name, GPU UUID / index, batch job, private log location) from the provenance of the reference schemas it knows, deterministic and idempotent; every key outside the provenance stays byte-identical (`verify` proves it against git); unknown schemas and reformatted files are refused |
| `hpcperf_golden_audit.py` | read-only consistency audit: every reference vs its registry input (spec, args, workload, provenance ancestry, sources changed since freezing, blobs), every golden benchmark's ctest and registry check vs the golden run, non-golden mechanisms, Level 2/3 `validate.sh` CPU gating, tolerance vs d0 / rounding; JSON + table, exit 1 on a HARD finding |
| `golden_artifacts.lock.yaml` | the committed lock of the bundles (sha256, size, members; `status: unpublished` until the maintainer publishes) |
| `tests/run_all.sh` | CPU-only tests (fake repository and benchmarks; no GPU); also runs `tests/test_golden_artifacts.sh` |

## Switches

| variable | effect | who sets it |
|---|---|---|
| `HPCPERF_CPU_REFERENCE=1` | the benchmark runs its own CPU reference and prints its pass line; also enables the offline CPU cross-check scripts of Level 2 (`check_sequential.sh`, `check_reference.sh`, `validate.sh` offline mode) | **only** `hpcperf_golden.py make` (or a person, explicitly). `tools/inputs` measure/check and `tools/timing` drop it from the environment; `tools/timing` cases cannot set it |
| `HPCPERF_GOLDEN_DUMP=<dir>` | the program writes each declared output to `<dir>/<name>.bin` plus one line in `<dir>/manifest.jsonl` (name, dtype, count, bytes, sha256) | the `check:` block (`run_env`), `make`, `run` |
| `HPCPERF_GOLDEN_MODE=hash` | record the sha256 only (huge outputs compared exactly, e.g. channel_shuffle's 23-30 GB) | the benchmark's `golden.mode` |
| `HPCPERF_SKIP_VERIFY=1` | unchanged meaning for the remaining property checks of the GPU output (lud, graph_coloring, binary_search's `verify()`, which runs by default next to the golden comparison); for every other converted benchmark it is implied | `tools/timing` |
| `HPCPERF_RANDOM_SEED=time\|<n>` | fir / color_histogram only: a non-registered random input (the registered inputs use seed 1); such a run FAILs the golden check, and tools/inputs, tools/golden run and tools/timing never pass it on | a person, explicitly |
| `HPCPERF_GOLDEN_STORE=<dir>` | where the raw bytes of tolerance-compared outputs live (default `<repo>/.golden-store`) | the environment |

Call sites capture **after** the timed region (ROI) and after the final device-to-host copy;
with no `HPCPERF_GOLDEN_DUMP` the capture is a no-op, so timing is unaffected.

## The registry (`inputs.yaml`)

```yaml
golden:
  mode: data                      # data | hash
  binary: build/level2/<app>/...  # run.sh entries only: the executable run.sh launches (provenance, staleness)
  cpu_check:                      # how `make` validates the capture ONCE
    pass_regex: '^PASS$'          #   the CPU reference's own pass / fail lines
    fail_regex: '^FAIL$'
    command: [python3, '{bench_dir}/verify.py', '{exe}', '{args}']   # optional: an external checker that runs the binary
    after_run: true               # optional: run the plain GPU command first, then `command` validates THAT run ({log})
    env: {KRIPKE_SEQ_LOG: '{run_dir}/sequential.log'}                # optional, templated
  outputs:
  - name: p                       # or match: <regex> + count: N (many captures with one rule)
    dtype: f32                    # f32 f64 i8 u8 i16 u16 i32 u32 i64 u64
    rule: {metric: max_abs, tol: 1.0e-3}
    cpu: p.cpu                    # the CPU-reference capture (d0); or {log: {file: <template>, regex: ...}}; or null
    basis: <the upstream check this reproduces, file:line>
  # Level 2: an output printed in the log instead of captured
  - name: particle_count
    dtype: f64
    log: {regex: '^\s*iter \d+: particle count=(?P<value>[0-9.eE+-]+),'}
    ...
check:                            # the registry's correctness check (tools/inputs/README.md)
  kind: post_run
  run_env: {HPCPERF_GOLDEN_DUMP: '{run_dir}/golden-capture'}
  command: [python3, '{repo}/tools/golden/hpcperf_golden.py', check, '{bench_dir}', '{input_id}', --dump, '{run_dir}/golden-capture']
  pass_regex: '^PASS: golden check'
  fail_regex: '^FAIL: golden check'
  covers: all
```

Rules (each reproduces the benchmark's existing check -- metric and tolerance -- or a documented project criterion where that check was missing or blind; the source is cited in `basis`):

| metric | value | used for |
|---|---|---|
| `exact` | sha256 equality | integers, permutations, bitwise-checked outputs (memcmp / ==) |
| `max_abs` | max \|a - g\| | e.g. adam, bilateral_filter, black_scholes, burgers_equation, nbody positions / velocities, hotspot_3d's gate |
| `max_rel1p` | max \|a - g\| / (1 + \|g\|) | RAJAPerf `compareArrays`, spadd, spgemm, backprop, hotspot, nearest_neighbor |
| `max_rel` | max \|a - g\| / \|g\| | pagerank, Kripke, nbody kinetic energy |
| `max_relabs` | max \|a - g\| / (rtol \|g\| + atol), tol 1 | ExaCMech |
| `l1_rel` | Σ\|a - g\| / Σ\|g\| | bezier_surface |
| `l2_rel_sq` | Σ(a - g)² / Σg² | spmv |
| `rmse` | sqrt(mean (a - g)²) | hotspot_3d |
| `trunc_int` | max \|trunc a - trunc g\| and the share of pixels that differ by >= 1 | srad_v1 (an (int)-written image) |

A non-finite value where the golden is finite always fails; an output of another shape fails; a
capture whose bytes do not match its recorded sha256 fails; a missing golden blob fails.

## Tolerance budget

`make` also captures the CPU reference's own array (`cpu:`) and records
`d0 = metric(B200 golden, CPU reference)`. The check allows `tol_effective`, chosen so that by the
triangle inequality a candidate within `tol_effective` of the golden is within (<=) the
benchmark's tolerance (upstream's or the documented project criterion) of the CPU reference --
replacing the CPU reference by the golden does not loosen the criterion:

| metric | tol_effective |
|---|---|
| `max_abs`, `rmse` | `tol - d0` |
| `max_rel1p`, `max_rel`, `l1_rel` | `(tol - d0) / (1 + d0)` (the golden's magnitude in the denominator is at most `1 + d0` times the CPU reference's) |
| `max_relabs` (tol 1) | `(1 - d0) / (1 + rtol d0)` |
| `l2_rel_sq` | `((sqrt tol - sqrt d0) / (1 + sqrt d0))^2` |
| `trunc_int` | `tol - d0` levels and `frac_tol - share0` (share of pixels >= 1 level apart: conservative) |

Outputs compared exactly need no budget: the original check already proved golden == CPU
reference bit for bit. A tolerance output without a CPU-reference capture (`cpu:`) is refused by
`make`: an unmeasured d0 would make `tol_effective = tol` looser than the original check.

## `make`: the one-time, CPU-validated freeze

```bash
python3 tools/golden/hpcperf_golden.py make level1/adam n10000-t200     # or --all
```

It refuses (exit 2) when: the benchmark directory, the tool files that capture / compare
(`hpcperf_golden.py`, `hpcperf_golden.h`, `hpcperf_golden_capture.py`) or `tools/timing/roi` have
uncommitted changes (a golden comes only from committed, unmodified sources -- never from an
optimization candidate or an agent workspace); the binary is older than its sources; a reference
already exists (replacing one needs `--replace --reason "..."`, and the new file records what it
replaced). It runs the build once with `HPCPERF_CPU_REFERENCE=1` and `HPCPERF_GOLDEN_DUMP`
(or, `after_run`, the plain GPU run and then the CPU cross-check of that run), requires the CPU
reference's pass line, exit 0 and no fail line, measures d0 per output and writes:

* `<bench_dir>/reference/<input_id>.json` (schema `hpcperf-golden-1`, **committed**): the workload
  identity of the input, the frozen spec, per output dtype / count / sha256 / statistics / rule with
  `d0_vs_cpu_reference` and `tol_effective`, and the provenance (the platform: GPU name, driver and
  compute capability, CUDA Toolkit; git HEAD, binary + sha256, the repository-relative command, the CPU
  validation's pass line and log sha256, the tool's own sha256). No host name, GPU UUID / index or
  absolute path of the machine is recorded (a `--workdir` outside the repository is `<workdir>/...`);
  the references made before 2026-10-28 had host and GPU UUID removed by `scrub_provenance.py`, which
  records `provenance.scrubbed` (what was removed, never the value) and leaves every other byte as is;
* for tolerance-compared outputs, the raw bytes in the content-addressed store
  `$HPCPERF_GOLDEN_STORE/sha256/<aa>/<sha256>.bin` (**never in git**; large).

After committing new or replaced references: `python3 tools/golden/golden_artifacts.py pack --staging
$HPCPERF_ARTIFACT_STAGING/golden` and commit the regenerated `golden_artifacts.lock.yaml` (`lock-check` must say
CURRENT); bundles of unchanged benchmarks keep their names and bytes. A fresh clone has no store: `python3
tools/golden/golden_artifacts.py fetch [level1/<b> ...]` installs the verified blobs (DISTRIBUTION.md) -- until the
bundles are published only with `--from <the maintainer's staging directory>` or a filled cache; until then a
tolerance-rule check FAILs with "golden blob ... missing" (never a fallback).

## The correctness gate (optimization candidates)

`check` and `run` read the registry and the frozen reference only from the canonical benchmark directory
(`<repo>/level<N>/<name>`); a copy -- an optimization candidate's workspace -- is refused, so a candidate can
never supply its own reference or rules, and `make` refuses a copy as well. `run --exe <candidate binary>`
runs that binary on the registered input (no CPU reference, capture into a private directory) and compares;
The reference itself counts only when it is committed in git and unmodified (`reference_committed` in the
verdict; an untracked or edited `reference/<input>.json` is a FAIL -- `HPCPERF_GOLDEN_ALLOW_UNCOMMITTED_REFERENCE=1`
lets tests proceed, prints a warning and records `reference_committed: false`, which is never an acceptance).
`--json <file>` writes the machine-readable verdict (`hpcperf-golden-verdict-1`: verdict, reason, every
output's metric value and limit, the reference file and its sha256, the binary and its sha256, the command,
exit code). An optimization harness accepts a candidate's timing only with a PASS verdict whose
`binary_sha256` is the sha256 of the binary it timed. Exit 0 only for PASS; a missing reference, a missing or
corrupted blob, a changed spec, another workload, a missing or partial capture, a non-zero exit are all FAIL.

### Wiring an optimization harness to the gate

Rules for any harness that accepts LLM-generated candidates (PerfSkills or another):

1. Every candidate's timing is accepted only together with a golden PASS of the **same binary**: the verdict
   JSON's `run.binary_sha256` must equal the sha256 of the binary that was timed (or, stronger, the timed run
   itself captures -- `HPCPERF_GOLDEN_DUMP=<per-run dir>` in its environment, the capture is outside the ROI
   -- and `hpcperf_golden.py check <canonical bench_dir> <input> --dump <that dir> --json ...` judges that very
   process).
2. The gate is `hpcperf_golden.py run|check` against the CANONICAL `level<N>/<name>` directory -- never against
   the candidate's copy (refused anyway). Exit 0 / `"verdict": "PASS"` is the only accepting state.
3. Do not rely on a harness default. Measured 2026-10-27 with PerfSkills `shared/scripts/bench.py`
   (`--oracle "python3 tools/golden/hpcperf_golden.py run level1/adam n10000-t200 --exe <candidate> ..."`):
   a wrong candidate (half the Adam steps, 1.11x faster) is recorded `correctness: failed` (golden max_abs
   0.549 > 9.8e-4) -- but bench.py still exits 0 and still reports the speedup, so the harness must gate on
   `correctness.status == "passed"`; PerfSkills' experiment controller excludes failed candidates from
   confirmation, but with no `oracle` in the plan it falls back to the exit code (`returncode`) -- a plan
   without the golden oracle has no correctness gate at all.
4. `HPCPERF_SKIP_VERIFY` during timing is fine: no CPU reference runs anyway, and the gate is a separate,
   explicit step that the acceptance rule requires.
5. A candidate's process should not be able to read the golden store or write the canonical tree (run it
   from its own workspace, with the store and the repository read-only or absent): otherwise a program could
   copy the frozen outputs instead of computing them.

`store-put <file>` / `store-get <sha256>`: content-addressed storage of a frozen reference that is a file
rather than captured arrays (e.g. a plotfile archive); `store-get` verifies the sha256 and fails when the
blob is missing or corrupted.

## Cost

The capture computes SHA-256 with the system's libcrypto when it can be dlopen'ed at run time (CPU SHA
instructions: ~2 GB/s on the Xeon 8570; `HPCPERF_GOLDEN_PORTABLE_SHA=1` forces the portable code, ~0.2 GB/s);
the digest is the same. Measured on a B200 (capture overhead on top of the plain run / Python comparison):
channel_shuffle g2-w224-h224 (23 GB, hash) +24 s / 0.3 s (was +125 s); bezier_surface n8192 (0.8 GB)
+1.3 s / 3.2 s (was +5.0 s / 8.2 s); burgers x8200 (1 GB) +1.6 s / 2.6 s; spgemm m100000 +3.1 s / 2.5 s.

## `check` / `run`

`check` reads the frozen reference and the run's capture (or, for log outputs, the run's log),
verifies the workload identity and that the registry's spec still equals the frozen one (a rule
changed after freezing is a FAIL until an explicit `make --replace`), compares every output and
prints `PASS: golden check <bench>/<input> ...` or `FAIL: golden check ...` (exit 0 / 1). It never
runs a CPU reference and never writes a reference. `run` (the ctest entry) runs the binary once
without the CPU reference, capturing, then checks.

## What is not a golden comparison

* NPB `cg ep ft is mg`: official class reference values (unchanged).
* `lud`: reference-free, the captured factors' residual max |A - L*U| <= 1e-4 (upstream's criterion, evaluated in
  float64 after the run by `level1/lud/lud_residual_check.py`, ~2 s at -s 8192; upstream's single-thread O(n^3)
  host recomposition runs only with `HPCPERF_CPU_REFERENCE=1`). `gaussian_elimination` (residual of the printed
  solution), `graph_coloring` (validity; its valid colorings are not unique and differ run to run): property
  checks, unchanged.
* `ao_bench`: already a frozen B200 image hash (`reference/iter100.sha256`), unchanged.

## Known limitations (2026-10-28)

Nothing below is a failing check: on the branch head every ctest, registry check and validate.sh default path listed
in the per-level READMEs passes (Nyx heat/cool stays PENDING, exit 3, as before). These are the limits of what the
checks can see, and what has not been run.

Limits of the checks (by design or not closable by a tolerance):

* **Repetition counts.** A benchmark that repeats an idempotent kernel for timing (most RAJAPerf / HeCBench ports,
  pagerank's timed repetitions, binary_search's variants) is checked on the output of the last repetition; running it
  fewer times leaves the output unchanged. The golden check validates the computation, not the amount of repeated
  work (no launch-count or grid requirements, by policy); a fixed workload is the measurement protocol's job
  (`tools/timing`: fixed arguments, the benchmark's own timer / ROI), and is not audited here.
* **Converged or near-steady-state inputs.** Where the registered performance input has converged (pagerank after
  ~12 of 500 iterations, hotspot_3d at 10000 steps where one step is 6.3e-4 RMSE, below the legitimate f32 envelope),
  a skipped late iteration is invisible in that input; the correctness probes (`purpose: correctness-probe`:
  pagerank `nodes16384-m5`, hotspot_3d `g64-l8-i50-amp10`, hotspot `g512-p2-t21-pnoise9`, ...) catch it, the
  performance input does not.
* **Accepted gray cases.** pagerank: renormalising every iteration or using exact 1/outdegree values differs from the
  defined (unnormalised) output only by a uniform factor 1 + ~1e-5 and passes (level1/pagerank/README.md, "Scale-only
  variants"); whether the scale is part of the contract is the owners' call. hotspot_3d: a stale halo (1.2e-2 K) or a
  uniform offset below 1e-2 K passes the performance inputs (the probe catches the halo). needleman_wunsch: a skipped
  top-right tile reaches no optimal path and leaves the output identical; the DP matrix is not compared. block_scan:
  the check is the scan of the whole input, independent of the block / grid configuration -- per-block tile
  semantics would need a redesign (future work, class E).
* **Exact rules define tie-breaking.** Outputs compared exactly (needleman_wunsch traceback with upstream's tie
  order, block_scan, the integer outputs) reject an implementation that resolves ties differently even when it is
  valid; nearest_neighbor refuses a registered query tied at the k-th distance instead.
* **Coverage of inputs.** References exist for the registered inputs only; sizes outside them are not validated
  (bezier_surface refuses `-n` outside 2..13377; binary_search's float query correction is general, its references
  are the three registered sizes). color_histogram x16777216 has a near-constant golden and no probe.

Not run (untested, never claimed):

* Other GPUs: every reference was made on one B200 node (CUDA 13.2, driver 595.58.03). Cross-architecture headroom is
  estimated from legitimate variants run on the B200 (fmad off, fast-math, f64 / Kahan accumulation, other block
  sizes, cuSPARSE), not measured on H200, MI355X or any other device.
* HIP: no ROCm on the node; every HIP port is edited in step with CUDA where a fix applied and never compiled.
* Publication: the bundles are packed and locked (`unpublished`, redistribution `review`); a fresh clone restores the
  store only with `fetch --from <staging>` until the owners publish them.

Open items for the owners (findings, not failures):

* Upstream reports not filed: srad_v1's reduction bug, hotspot3D's N-1 final iterate and nearest_neighbor's
  findLowest lost-record swap are fixed here (class D, per-benchmark README) and could be reported upstream.
* Pre-branch Level 2 references (nekbone, pennant, picongpu, vpic, hipbone, miniweather, branson cases) still name the
  node in `host` / notes; `level2/branson/check_log.py` and `level2/remhos/check_cpu_backend_reference.py` would
  record host data in a future re-freeze.
* `level3/nyx/validate.sh` in offline mode rewrites `<run>/.np_final` (same value) inside historical run directories.
